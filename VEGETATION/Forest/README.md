# Dense canopy forest — DF0/DF1/DF2

**Status:** DF0–DF2 and DF2.5 implemented in source; local Godot/.NET and DF2.5 visual validation pending. DF3–DF5 remain planned.

The shared World and FPS scenes now support a **conditional dense, high-canopy broadleaf strip** east of the village, extending north parallel to its other buildings. The forest is **enabled in `Configuration/ForestMaster.tres`**. DF2.5 extends the former 96 × 96m square to **96m east/west × 256m north/south**, centred at X/Z **(667,487)** (bounds X 619–715, Z 359–615); it keeps the original southern area and the original entry around Z 567. DF0 surveys Terrain3D and the road approach. Existing village/robot/actor reservations now reject individual tree candidates with a 2m safety margin rather than disabling the entire longer strip for a small overlap. If the site is unwalkable or mostly obstructed, **no new trees are created and old pines remain**.

## DF2 gameplay integration

- `ForestPlacement.cs` builds an irregular, seeded layout from DF1's three tall canopy variants and smaller, simplified filler trees; mature/filler candidate spacings default to 7m/8m, with configurable densities and minimum trunk separations.
- Trees are grouped into **32m chunks**, with shared near/far Mesh templates and `MultiMeshInstance3D` batches. Each loaded chunk owns one static body with capsule colliders only at trunks (same physics layer 5 as pines).
- A winding **7m east–west entry corridor**, a narrower meandering **north–south interior route**, and two small clearings keep the longer zone traversable. Terrain3D height and slope are sampled once for candidate tree roots; no runtime terrain writing.
- New canopy foliage uses one shared opaque shader, which permits **top-down-only per-tree camera fading**. FPS displays full leaves. Near trees cast shadows by default; far trees do not. DF3 will refine canopy light blocking.
- The patch excludes old random pines **and random rocks only inside the successfully approved footprint**. Grass remains, ready for DF4 undergrowth integration.

## DF2 white-tree recovery, safe palette trial (2026-10-31)

Two separate screenshots showed the DF2 canopy and bark almost white despite previous shader fallback changes. We cannot confirm the exact cause from screenshots alone. **To isolate the rendering path and restore clearly coloured scenery, `Configuration/ForestMaster.tres → UseSafePaletteMaterials=true` is now ON by default.** DF2 binds two independent native Godot `StandardMaterial3D` surfaces (brown-grey bark and foliage green from `CanopyTreeMaster.tres`) and *explicitly* assigns them after `SurfaceTool.Commit`. This avoids dependence on the unverified custom shaders or vertex colour attribute for the visual baseline. **Tree geometry, height, seeded placement, MultiMesh batching, near/far distances, collision and shadows remain unchanged.**

**Trade-off while safe mode is on:** DF2's individual per-tree **top-down foliage fading is temporarily disabled** (native materials do not consume the old INSTANCE_CUSTOM opacity), and the subtle DF1 per-face colour variations are simplified into two solid shared palette colours. The existing F1 global foliage colour/strength controls are mirrored onto the one safe foliage material at startup and whenever either control changes (no per-tree loops). Stylized pines and grass still use their original shader global implementation. After confirming bark and canopy are coloured, setting `UseSafePaletteMaterials=false` restores the custom DF2 shaders, top-down fade and original authored vertex colours.

**Crucial diagnostic:** Godot Output now prints one line at forest initialization: `DF2 COLOR CHECK [SAFE]: bark=StandardMaterial3D, leaves=StandardMaterial3D, base leaf=...`. This validates material attachment before creating chunks, and logs an error if one of two expected surfaces is missing. With safe mode OFF it prints `[SHADER]`. If the trees remain white, collect this line plus any red shader/import errors, because the issue would no longer be explained by the custom foliage shader alone. Local `dotnet build`/Godot visual acceptance pending.

**GV1 shared visibility:** `ForestSettings.cs` and `ForestMaster.tres` no longer author DF2 visibility limits. Both broadleaf LOD batches use the shared `VegetationVisibilityPolicy` (LOD0 to 35%, LOD1 to opaque fog + 24m initial safety band). Increasing or decreasing FPS/World distance fog changes the actual loaded 32m chunks, ranges and GPU load through one event; placement and the safe-material DF2 recovery are unchanged. [Global master](../Configuration/README.md#gv1--one-global-fog-linked-vegetation-range-2026-10-31).

## DF2.6 — 50/50 original and leafier broadleaf canopy (2026-10-31)

**Implemented in source; compile, visual and FPS acceptance pending.** `ForestMaster.tres → LeafierShare=0.5` uses a separate deterministic hash per accepted candidate for approximately half the trees to use the new `CanopyTreeLeafierMaster.tres` geometry. Set `0` for the untouched all-original DF2.5 forest, or `1` for all-leafier art; values in between are seeded probabilities, not an exact per-chunk quota. This does **not** change the DF2.5 96 × 256m strip, forest seed, candidate density, positions, scale, yaw, entry/clearings, trunk collisions, fog-linked visibility or 32m chunk ownership. Each tree is assigned one of 12 cached visual bins (3 mature + 3 young for each style) and the existing near/far MultiMesh system; no extra forest node, simulation/physics tick or shader. The extra style bins can increase draw calls in populated chunks; local FPS should be compared at the same viewpoint.

The original mesh/resource remains unchanged, while the leafier mesh has subtle angular leaf sprays and modest upper-trunk refinement. Default safe Godot materials continue to colour both styles without the earlier white foliage issue. Godot Output now includes `DF2.6 canopy: N original / M leafier`. For visual inspection, open `VEGETATION/Trees/CanopyTree/CanopyTreeLeafier.tscn` beside the original `CanopyTree.tscn` after a .NET build, and walk the east forest in the FPS world. Build and local render tests were not performed in this change.


## DF2.7 — tiny, deterministic tree lean (2026-10-31)

**Source implemented; awaiting build and visual validation.** `ForestMaster.tres → MaxTiltDegrees=1.5` gives both original and leafier mature/young tree styles an independent seeded 0–1.5° lean around a random horizontal direction. Set **0** for completely upright trunks; the exported range caps maximum tilt at **2°**. The same tilt matrix is used for near/far MultiMesh transforms and for each trunk's capsule collision (no collision mismatch). Tree positions, yaw, scaling, mixture, seed, 32m chunk ownership, visibility/LOD, terrain and forest footprint remain untouched. Angle generation is startup-only; no per-tree processing. Check in FPS that bases remain grounded and that trees do not appear noticeably slanted or slide during LOD transitions.

## DF2.8 — multiple authorable forest zones (2026-10-31)

**Integrated in source; local Godot/.NET compilation, terrain approval and FPS checks still needed.** Forest zones belong under `VEGETATION/Forest/`, not `WORLD/Terrain/`: they determine WHERE existing canopy trees grow, without modifying terrain heightmaps, landscapes, materials, grass, or structures.

**Authoring:** `Configuration/ForestZonesMaster.tres` is an ordered, typed list of `ForestSettings` resources, referenced from `WORLD/Configuration/WorldMaster.tres → ForestZones`. Zone 1 uses the original `ForestMaster.tres` unchanged (centre 667/487, size 96×256m, seed 72199, village approach and trails preserved). The two enabled examples are `ForestWestWoodMaster.tres` (365/690, 144×160m, mature/young density 0.82/0.65) and `ForestSouthEastWoodMaster.tres` (790/745, 144×160m, density 0.92/0.70). New sample locations are **tentative**; source-level GitHub changes cannot inspect the user's saved local Terrain3D heights. On F6, Output lists `DF2 zone N approved` or the terrain/slope/overlap rejection reason. Edit `CenterXZ` and `SizeXZ` if needed, or toggle `Enabled` per zone. Duplicate/create another `ForestSettings` resource and add it to the array to author more (first 12 entries bounded for predictable startup). If the array is absent/empty, legacy `DenseForest` is used.

**Safety:** `ForestZonesPlacement.cs` (one world-owned Node3D) surveys all zones on startup against the original road, village, spawn and wildlife exclusion rectangles; only safe, nonoverlapping, enabled regions suppress pine and rock candidates within their surveyed core. Per-tree original reservations stay intact. Extra woods set `RequireVillageApproach=false` so they don't require an arbitrary straight footpath from the town; Zone 1 retains its original approach check. Rejected zones do not erase existing vegetation. Grass and billboard patterns are untouched, including grass beneath canopy.

**Rendering:** each approved zone instantiates the unchanged DF2 placement logic (original/leafier canopy mix, lean, collision, native near/far MultiMesh and 32m chunk streaming), all reading the same GV1 fog-driven visibility policy. F1 shared leaf tint and top-down obstruction checks fan out through the single zone owner. The manager has no idle frame/physics loop; only existing player-position and LOD events trigger work. Each zone currently builds its own canopy mesh templates once, so many zones increase startup mesh memory; optimize with shared templates later if profiling warrants it. Test F6 FPS and World, inspect Output, F1 tint, distant unloaded zones, trunk collision and performance locally. No new biome engine or terrain baking.

## FV1 — safe-palette shared tint initialization (2026-10-31)

DF2 forests no longer read shader global uniforms back from `RenderingServer` on each zone startup (Godot emitted a render-thread synchronization/runtime performance error). `ForestZonesPlacement` passes one CPU-owned `FoliageTintSettings` runtime copy from `WorldController` to each unchanged `ForestPlacement`; its safe leaf material applies `Tint` and `Strength` at initialization. F1 still pushes edits to every zone's one shared safe leaf material, while original leaf shaders and all vegetation placement/chunk/LOD rules remain unchanged. Author the tint under `VEGETATION/Configuration/FoliageTintMaster.tres`, not by reading `project.godot` globals. Local FPS/World visual check pending.
